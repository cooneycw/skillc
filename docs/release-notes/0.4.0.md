# 0.4.0

Closes four issues, all found and fixed along the way rather than
predeclared as a capability milestone: [#159](https://github.com/cooneycw/skillc/issues/159),
CPP scan suppressions; [#174](https://github.com/cooneycw/skillc/issues/174),
three load-sensitive tests made deterministic; [#189](https://github.com/cooneycw/skillc/issues/189),
a silent partial-capture bug in the Docker backend's own output draining;
and [#186](https://github.com/cooneycw/skillc/issues/186), a silent
failed-write-back bug in the same backend that let a subject suppress its
own capture entirely. **No new capability milestone closes this cycle** -
substantial code landed for #13 and #14 (below), but both stay open, each
still owed a real live-agent run.
Full detail: [`CHANGELOG.md`](https://github.com/cooneycw/skillc/blob/v0.4.0/CHANGELOG.md)'s
`[0.4.0]` section.

## #159: CPP scan suppressions

CPP's `/flow:auto`/`/flow:finish` security gate (`python3 -m lib.security
gate flow_finish`) is CPP's own native pattern scanner, not gitleaks, and
does not read `.gitleaks.toml` - so skillc's existing gitleaks allowlist did
nothing for it, and skillc's own planted fake keys (an AWS trial-capture
canary, an Anthropic API key test fixture) blocked every CPP-run finish gate
on skillc, 12 times across about 10 runs on 2026-09-26/27, each overridden
by hand. `.claude/security.yml` declares exact-value suppressions for the
two planted canaries (CPP PR #1312's `secret:` field), value-pinned, not
file-wide: a red case appended a different fake key to an already-suppressed
file and confirmed the gate still blocks it. Verified against a real CPP
gate run: `blocked=4` before, `blocked=0` after, no `GITIGNORE_GAP` warning
with the file tracked despite `.gitignore`'s own pre-existing line for it.

## #174: three load-sensitive tests made deterministic

Three tests read as flaky under host load, two of them past quarantine/
disposition messages that must never be trained away: `collection-run`'s
disposition read `inconclusive` instead of `captured` once under load 70/24
cores; `tests/test_selection_probe.py` failed six tests under load with
"this verifier is quarantined"; and the drain-EOF red case for #133 item 3
failed once in a full `make verify` run. Root cause for the first two,
shared: `DockerBackend._inspect()` bounds `docker inspect` at
`daemon_timeout` (production default 5.0s), and neither test's
`DockerBackend` construction overrode it, so a slow `docker inspect` under
contention crossed that bound and `confirm_stopped()` correctly answered
`UNKNOWN` (fail-closed) - which one caller turned into `inconclusive`, the
other into a quarantine. Fixed with a shared TEST-only wider bound
(production's own bound is untouched), reproduced deterministically by fault
injection (a new `.inspect-delay-NAME` sentinel in the fake `docker` CLI)
rather than host load, after the original load-based plan would have
collided with a teammate's own full-suite run on the shared host. The
drain-EOF test's own timing assertion had ~zero margin even at nominal
bounds; fixed by construction (a FIFO the subject blocks on, instead of
racing a fixed `sleep 8` against the join bound).

A follow-up nit found while fixing this (`tests/test_leak.py`'s own
host-paths test depended on the ambient checkout location) is fixed too:
chdir into a deterministic path outside `/home`/`/Users`, matching an
adjacent test's own established fixture shape.

## #189: a silent partial-capture bug in the Docker backend

Found while fixing a related latency issue in the same code
(`DockerBackend.execute()`'s and `read_home_tree()`'s stdout/stderr drain
joins ran sequentially, doubling worst-case teardown latency - measured
directly at ~2.08x/~2.02x the single bound before the fix, ~1.08x/~1.02x
after; both now join against one shared deadline). `_BoundedDrain.run()`
read with `IO.read(65536)`, which on a non-interactive stream may issue
multiple underlying reads to fill the FULL requested size, blocking until
either that much data arrives or EOF - so a subject that wrote some output
(under 65536 bytes) and then left the pipe open without writing more or
closing it was captured as **nothing**, silently, contradicting the
Docker backend's own bounded-capture rule and `ExecuteResult`'s
`stdout_incomplete`/`stdout_bytes` design (both promise "captured what we
could, marked incomplete", never "wrote data, captured zero, no error").
Fixed by reading with `os.read()` on the raw fd instead - one syscall,
returns whatever is currently available. A committed red case (a 10KB write
held open, no docker/subprocess involved) fails on the pre-fix code and
passes after, asserting both halves of the acceptance together (captured
AND still-incomplete, not two separate assertions a partial fix could
satisfy piecemeal); a positive control beside it proves the ordinary
EOF-close path still captures everything (200KB, several times the read
size). Checked and documented: nothing else reads the same pipe objects
through the buffered API before or during the drain, at either call site -
switching the first read from the buffered API to a raw one cannot skip
data an untouched `BufferedReader` was never holding.

## #186: a silent failed-write-back bug, and a structural INCONCLUSIVE fix

Found reviewing #14's L4 follow-up. `DockerBackend.execute()` writes the
exec'd process's captured stdout back into the workspace via `docker cp -`
(a tar stream), run with `check=False` and its result never inspected - so
a subject that pre-creates `/work/observations` as a symlink to a directory
made the tar extraction fail with `IsADirectoryError` completely silently:
no exception, no `ExecuteResult` field, the subject's own object left in
place, the real capture never landing. `ExecuteResult.observations_capture`
now names the checked outcome (`"written"`/`"failed"`, never swallowed).
Red case: a directory symlink at `observations` fails on pre-fix code with
`AttributeError: 'ExecuteResult' object has no attribute
'observations_capture'`, not merely a wrong value.

A second bug, found while answering "what does each `observations` reader
do with this state": `verify.py`'s own `_read_untrusted` claimed "None when
not a readable regular file", but actually CRASHED on a directory -
`os.open()` succeeds opening a directory `O_RDONLY`, so the `S_ISREG` check
running only after `os.fdopen()` was too late. Fixed by checking `S_ISREG`
on the bare fd first. `AuthorityInterceptor`'s directory-symlink handling
for `observations` is refined the same pass (a Nit Store follow-up to #14,
same root cause): a directory symlink there is now recorded immediately,
never deferred for settled-value resolution the way a regular file is,
since the write-back can never produce a directory.

**A failed capture now grades INCONCLUSIVE, structurally, in one place -
not reporting-only (orchestrator review).** Naming `observations_capture`
was not enough by itself: nothing consumed it, so a failed write-back still
read as an empty report and graded FAIL - a measurement that did not
complete, asserting the candidate did something wrong. All five existing
eval tasks already refused to read an empty/malformed report as success
(checked, not assumed), which is why this happened to be safe today - but
that was a per-judge convention, not a structural guarantee. Fixed once in
`verify.py`'s `_probe_via_backend`/`grade_files`: a failed write-back makes
`category = "capture"`, every criterion UNKNOWN, `status` INCONCLUSIVE -
the judge never runs, for every grader, no judge changes needed. Scope
limit, stated plainly: fake-CLI-verified only - a real daemon's `docker cp`
extraction over an existing directory symlink is untested here, per the
standing no-real-daemon limitation.

## What else shipped in this cycle

- **`--task DIR` on `skillc demo` and `skillc selection-probe`**
  ([#20](https://github.com/cooneycw/skillc/issues/20) Nit Store, PR #187),
  mirroring `collection-run`'s own `--task`: both commands hard-coded
  `evals/level1/slug-small-fix` and could not be pointed at a different
  Level 1 task without a code change. `demo --control` (the seeded negative
  controls) is refused together with `--task`, since its known-bad candidate
  is specific to the default task's own `wrong/` fixtures - a per-task
  control needs a declared control candidate in the task itself, its own
  future change. Both defaults are unchanged without the flag.
- **`skillc/authority_interceptor.py`, an L4 authority-boundary fixture
  service** ([#14](https://github.com/cooneycw/skillc/issues/14), PR #181,
  plus a report-supported coverage widening and an observations-exclusion
  fix in PR #190, and a symlink-to-a-directory visibility fix folded in with
  PR #185): polls a live attempt's WHOLE out-of-scope surface from outside
  the container, on a background thread concurrent with `execute()`, and
  assembles the `trusted_observation` bytes the L4/L5 judges now trust
  instead of a candidate-writable file's self-declared provenance. A real,
  committed blind spot remains and is stated plainly: a violation both made
  and undone strictly between two polls leaves no trace
  (`known-gaps/delete-then-restore/`).
- **`skillc/disruption_trigger.py`, an ADVISORY Level 5 request-count
  observer** ([#14](https://github.com/cooneycw/skillc/issues/14), PR #185).
  **Its output is never passed as `trusted_observation`, and Level 5's
  trusted channel remains unsolved** - the request log lives inside the
  same subject-writable workspace tree, so trusting its content (a line
  count) the way L4's diff trusts byte changes at a controller-decided path
  would let a subject fabricate the count with zero real work behind it. A
  real fix needs a controller-owned decide-and-reply channel, tracked as
  [#183](https://github.com/cooneycw/skillc/issues/183).
- **`skillc/verify.py` gains a trusted-observation channel**
  ([#14](https://github.com/cooneycw/skillc/issues/14), PR #177):
  `grade_files`/`grade_agent_attempt`/`grade` take an optional
  `trusted_observation: bytes | None`, delivered to the judge without ever
  passing through the probe or candidate code. `known-gaps/forged-log`
  correctly FAILs where it used to PASS undetected in both L4/L5 tasks.
  **Nothing in production supplies this yet** - the fixture services that
  do (above) landed in this same cycle, but a real L4/L5 attempt still
  grades `stayed-in-bounds`/`work-preserved`/`report-supported` UNKNOWN.
- **Declared, per-criterion outcome dimensions**
  ([#13](https://github.com/cooneycw/skillc/issues/13), PR #191):
  `grader.json` gains an optional `dimensions` field
  (`functional`/`constraint`/`integration`), DECLARED, never inferred from a
  criterion id's own naming. `skillc/outcome_report.py` groups a graded
  record's criteria by this declaration and derives each bucket's own
  verdict, surfaced in both `collection-run`'s paste-back and
  `pilot-run`/`pilot-report`'s exported entries. Level 2 and Level 3 declare
  dimensions for every criterion; Level 1, L4 and L5 declare none today and
  report `unclassified`.
- **`skillc configuration-compare`, #13's other acceptance bullet**
  ([#13](https://github.com/cooneycw/skillc/issues/13), PR #193): pure
  post-hoc analysis of two already-captured evidence records. A closed set
  of identity fields (`task_id`, `grader_revision`, `image_digest`,
  `client`, `model`, `timeout_seconds`, `collection`) must match, or the
  comparison refuses and names every mismatch, with one field the caller
  may legitimately vary. Built and proven against a REAL `collection-run`
  attempt's actual saved artifacts, not fixtures written to the tool's own
  schema (review finding) - which surfaced two real gaps, both documented
  rather than papered over: `image_digest`/`timeout_seconds` are recorded
  in neither real artifact today (filed as
  [#188](https://github.com/cooneycw/skillc/issues/188), out of scope
  here), and the exported result's own `criteria` field mixes the
  verifier's `installation-ready` criterion in alongside the grader's,
  silently turning a genuine PASS into an INCONCLUSIVE dimension verdict if
  bucketed directly (fixed - `record["graded"]["criteria"]`, task-only, is
  the right source). Because of #188, a per-field `provenance`
  (`"recorded"`/`"asserted"`) prevents a comparison from reading as if a
  real record had proven a field neither artifact actually captured -
  unmentioned fields default to the weaker `"asserted"` claim, and
  `"recorded"` must be earned per field by an adapter that actually read it
  from a real artifact.
- **Capability-gated in-container TERM forwarding to the exec'd subject**
  ([#158](https://github.com/cooneycw/skillc/issues/158), PR #182): two new
  scripts let a container-level TERM reach the exec'd subject's process
  group for real - something no real Docker daemon does on its own. Inert
  on every image today (probed before use, byte-for-byte the pre-#158
  behavior when absent); the Dockerfile change that would activate it stays
  HELD pending the operator's #150 discriminating run.
- **`docs/specs/evaluation-facility/signal-forwarding.md`**
  ([#158](https://github.com/cooneycw/skillc/issues/158), PR #178): the
  design doc for the supervisor/wrapper approach above.
- **The Makefile's local leak-check exclude list derives from CI's own**
  ([#20](https://github.com/cooneycw/skillc/issues/20) Nit Store, PR #184),
  instead of being hand-copied and free to drift: two committed tests parse
  both files' own exclude lists and assert they agree (plus the Makefile's
  one documented local-only addition), with a committed red case on each
  side and a positive control proving the parsers are not vacuously empty.
- **`fix(tests): fake docker kill/rm reap the exec'd subject like the real
  daemon`** ([#158](https://github.com/cooneycw/skillc/issues/158), PR
  #176): the fake `docker` CLI's `kill`/`rm` used to leave an exec'd
  subject running after a container-level kill, more capable than the real
  daemon it stands in for - fixed to model the kernel's own PID-namespace
  teardown instead of forwarding a signal.

## What 0.4.0 is not

- **Not #150's, #26's or #55's own live evidence.** All the producer-side
  code these issues need already exists (see 0.3.0's own release notes for
  what landed there); nothing in this cycle touched any of the three, and
  each stays open for the operator's own live run: #150's discriminating
  run (`docs/runbooks/150-discriminating-run.md`), which
  [claude-power-pack #1084](https://github.com/cooneycw/claude-power-pack/issues/1084)
  is blocked on; #26's single live run that exercises the detection control
  AND retains transcripts together; #55's surface-declaration layering
  signoff and a published evidence run against mattpocock/skills.
- **Not #158's live-daemon verification, and the image change stays HELD.**
  The supervisor/wrapper scripts that let a container-level TERM reach the
  exec'd subject exist and are inert on every image today; the Dockerfile
  change that would activate them is deliberately not made here, pending
  the operator's #150 discriminating run.
- **Not #14's real agent attempt, calibration, or Level 5's trusted
  channel.** The authority-boundary interceptor, the trusted-observation
  channel, and the advisory Level 5 observer all landed this cycle (see
  above) and self-certify locally; no live agent has attempted either
  level yet, and #14 stays open for that run, for calibration, and for
  [#183](https://github.com/cooneycw/skillc/issues/183) - the
  controller-owned decide-and-reply channel Level 5's trusted signal
  actually needs, which the advisory observer explicitly is not.
- **Not #13's real matched-configuration runs, and #188 is why a comparison
  run today could not fully prove its own identity claims from the stored
  record alone.** Both of #13's acceptance bullets now have real code:
  declared outcome dimensions and `configuration-compare` (both above).
  #188 - `collection-run` resolves the trial image digest and attempt
  timeout before running but persists neither - stays open; `compare()`'s
  `provenance` labeling (above) makes that gap visible in any comparison's
  own output rather than silently trusting a caller-supplied value, but
  does not close it. #13 stays open for a real matched-configuration run on
  the operator's own host, which has not happened yet.
- **Not a real judge call or a paid model trial.** #12's own scope ruling
  ([ADR 0005 rule 6](../decisions/0005-runtime-scope-and-cost-rulings.md))
  continues to apply; nothing in this cycle changes it.
- **The Nit Store (#20) stays open, by design** - it is evergreen, like
  this issue's own #72. Two findings from this cycle are folded into work
  above (the leak-exclude derivation, the drain-joins latency fix); a third
  (the sequential-join pattern in `read_home_tree()`, found while fixing
  the first) was folded into the SAME PR as the first, per orchestrator
  review, rather than left for a later pass.
